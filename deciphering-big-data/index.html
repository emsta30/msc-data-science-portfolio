Module overview

This portfolio presents selected learning evidence from Deciphering Big Data, including discussion participation, retrospective data-cleaning practice, AI-assisted healthcare data profiling, relational database development and evaluation of the final implementation against the original group proposal.

It distinguishes completed work from retrospective practice and documents limitations alongside technical outcomes.

Evidence files are being added. Only anonymised screenshots and non-sensitive project artefacts should be published.

Learning evidence

IoT data collection · Units 1–3

Activity: Critical evaluation of Internet of Things (IoT) data collection, considering opportunities, limitations, security risks and data-quality challenges.

Evidence: Initial discussion post (9 August 2026) and peer response (11 August 2026).

My initial contribution examined the opportunities presented by large-scale IoT data collection, particularly its potential to support real-time analysis and decision-making. Drawing on Huxley (2020) and wider literature, I considered the challenges associated with inconsistent data, interoperability, privacy and cybersecurity.

In my response to peers, I developed the discussion further by questioning whether maintaining comprehensive audit trails would be practical when processing continuously generated data. I explored the potential of data provenance and risk-based human review to balance transparency with scalability.

Learning and reflection: This discussion reinforced the importance of considering data security and governance alongside the technical benefits of collecting and analysing information. I have encountered similar considerations in my professional role, where I developed a Power BI dashboard containing sensitive financial information. When deciding how to share the dashboard with senior leadership, I recognised that password protection alone would not provide sufficient control over access. I therefore retained the dashboard within the organisation's Microsoft environment and arranged controlled access through Microsoft Fabric. This experience reinforced the importance of balancing accessibility with appropriate data protection measures.

Data cleaning and preparation · Units 4–5

Activity: Data-cleaning lecturecast and associated Python exercises, including dataset conversion, preparation and documentation.

Evidence: Retrospective Python exercise and supporting screenshots to be added following completion.

Using Python and Pandas in Google Colab, I retrospectively completed a data-profiling and cleaning exercise using the UNICEF survey dataset supplied with Data Wrangling with Python (Kazil and Jarmul, 2016). The dataset contained 9,008 records and 159 columns. Initial profiling identified mixed data types, extensive missing values and no exact duplicate rows. Three columns contained no recorded values and were removed from a separate working copy, while the original dataset was preserved. I recognised that missing survey responses may reflect questionnaire routing rather than errors, highlighting the importance of understanding data context before applying automated cleaning rules.

An important consideration is that cleaning data involves more than correcting obvious errors. Decisions about missing values, inconsistent formats and unusual observations can influence the reliability of subsequent analysis. Although automation can make these processes more efficient, it is necessary to distinguish between errors that can be corrected confidently and values that require further investigation.

Learning and reflection: A relatively simple task, importing CSV files into Google Colab, highlighted gaps in my technical understanding. Having initially saved the datasets using Apple Numbers, I encountered a FileNotFoundError when attempting to load them into Python. Resolving this required me to understand the difference between spreadsheet and CSV formats, the importance of file extensions and the need for filenames in code to match the uploaded files exactly. Although initially frustrating, the experience demonstrated that successful data analysis depends on understanding fundamental data-handling processes, rather than relying solely on AI-generated code.

These principles became particularly relevant during my later healthcare database project. While using Python to profile the dataset, I identified inconsistent patient demographics, invalid date sequences and discrepancies in recorded lengths of stay. Rather than automatically replacing questionable values, I preserved the source information and created validation indicators to identify records requiring review. This demonstrated how data-cleaning decisions can affect the integrity and usefulness of an analytical system.

AI-assisted group proposal · Unit 6

Activity: Collaborative development of a relational database proposal using a healthcare dataset.

Individual contribution: Investigation of AI-assisted data profiling and preparation using Google Colab.

My allocated responsibility within the group project was to investigate how AI could support data wrangling and database development. Using Google Colab, I applied Python scripts, some developed with AI assistance, to profile the healthcare dataset and investigate inconsistencies in the records. This included identifying discrepancies in admission and discharge dates, recorded lengths of stay and patient information. These findings informed the group's approach to data preparation and highlighted the need to preserve original records while documenting potential errors rather than automatically correcting them.

Learning and reflection: A significant finding was that Gemini suggested treating patient identifiers as stable keys, despite the dataset containing repeated patient IDs associated with conflicting demographic information. It also proposed resolving inconsistencies using the earliest or most frequently occurring value, although neither approach could establish which value was correct. This highlighted the limitations of relying on AI-generated recommendations without independent validation. I recognised that a technically plausible solution could introduce further inaccuracies if applied without understanding the underlying data. Consequently, the group proposed retaining original records, using generated internal identifiers and flagging questionable data for review rather than making unsupported corrections.

Supporting evidence: Unit 6 group submission, Google Colab notebook and relevant data-profiling outputs.

Database design · Unit 7

Activity: Exploring relational database design, normalisation and the implementation of structured datasets.

Evidence: Individual healthcare database implementation, SQLite validation results and relational database structure.

The principles of database normalisation became particularly relevant during my individual healthcare analytics project, where I transformed a flat dataset containing 10,000 hospital encounters into nine interconnected SQLite tables. This involved separating patient, clinical and operational information into related entities, with primary and foreign keys used to establish relationships and reduce unnecessary duplication.

One challenge was the unreliability of the original patient identifiers, which contained conflicting demographic information. Rather than assuming these represented verified individuals, I retained the source identifiers and introduced unique encounter references to preserve traceability.

Learning and reflection: This experience developed my understanding of the relationship between database structure and data integrity. Although the resulting database passed referential integrity checks, I recognised that a technically valid relational model does not necessarily guarantee accurate underlying information. This highlighted the importance of considering data quality alongside normalisation and database design.

Supporting artefacts: SQLite database structure, Python implementation and foreign-key validation results.

Governance and security · Units 8–10

Activity: Exploring data protection, information governance and security considerations associated with data processing, including API security.

Evidence: Healthcare database project evaluation and professional application of data-access controls.

The module's coverage of data governance and security highlighted the importance of protecting sensitive information throughout its lifecycle, from collection and processing to storage and presentation. These considerations were particularly relevant to my healthcare database project, where I evaluated the implications of processing patient information under UK GDPR and the Data Protection Act 2018.

I have also encountered similar challenges in my professional role, where I developed a Power BI dashboard using sensitive financial information. When considering how to present this information to senior leadership, I decided against hosting the dashboard online with basic password protection, as this would not provide the level of access control required. Instead, I retained the dashboard within the organisation's Microsoft environment and provided authorised leadership access through Microsoft Fabric.

Learning and reflection: This experience reinforced my understanding that effective data management extends beyond producing accurate analysis. Decisions about where information is stored, who can access it and how it is shared are equally important. It also highlighted the need to balance accessibility with confidentiality when communicating analytical findings.

Learning evidence

Unit 6 vs Unit 11 evaluation

The original group project proposed an AI-assisted healthcare database solution using a dataset of 10,000 hospital encounters. My individual responsibility focused on AI-assisted data profiling, using Google Gemini and Python within Google Colab to identify inconsistencies and evaluate automated recommendations.

The group proposed a normalised relational database, data-quality classifications and an interactive dashboard. My subsequent individual executive summary developed this proposal into a working nine-table SQLite database and R Shiny dashboard.

Implementation required several changes to the original design. Unreliable patient and doctor identifiers prevented some proposed relationships from being implemented confidently, while validation identified substantial inconsistencies in admission dates, lengths of stay and demographic information. Rather than automatically correcting these records, I preserved source values and introduced validation indicators.

The completed database retained all 10,000 encounters and passed foreign-key integrity checks. However, only 128 records were provisionally classified as valid without identified issues. This demonstrated that structural integrity does not guarantee reliable analytical information.

The transition from the group proposal to the individual implementation was particularly valuable because it required me to move beyond identifying potential solutions and assess whether they were feasible with the available data. The group project established the proposed approach to data profiling, relational database design and visualisation, but implementing these ideas exposed practical limitations. In particular, the inconsistent patient identifiers meant that relationships which appeared reasonable at the design stage could not always be supported by the source records. This reinforced the importance of treating database design as an iterative process, informed by data validation rather than assumptions about how the dataset should behave.

Developing the R Shiny dashboard introduced a further consideration: how to communicate complex information clearly without implying greater accuracy than the data could support. I created summary indicators for the 10,000 encounters, recorded readmission rate of 41.42% and average waiting time, alongside ward-level visualisations and interactive filtering. Although the dashboard made the information easier to explore, I recognised that presenting results professionally does not resolve underlying data-quality problems. The experience strengthened my understanding that effective data science requires not only technical implementation but also transparency about limitations and responsible interpretation of findings.

Critical reflection: The most significant development was my understanding of AI's limitations. Although AI-assisted code generation improved efficiency, its recommendations required independent testing and human judgement. The project shifted my focus from producing a technically functioning solution towards evaluating whether its underlying information was trustworthy.

Learning evidence

Professional development

Studying Deciphering Big Data has strengthened my understanding of the relationship between data preparation, analytical reliability and effective decision-making. Although my professional background is in marketing, my current role increasingly involves analysing information, developing dashboards and communicating findings to senior leadership.

One practical application has been developing a Power BI dashboard to present business performance information. This required me to consider not only how data should be organised and visualised, but also how sensitive financial information could be shared securely. I chose to retain the dashboard within the organisation's Microsoft environment, using controlled access through Microsoft Fabric rather than relying on basic password protection.

The healthcare database project has also developed my confidence in using Python and AI-assisted tools. Working with Google Colab demonstrated how AI can support unfamiliar technical tasks, while reinforcing the importance of testing generated code and questioning its recommendations.

These experiences have encouraged me to approach data analysis more critically. Rather than focusing solely on producing reports or visualisations, I now place greater emphasis on understanding the quality, limitations and security of the information on which they depend.
